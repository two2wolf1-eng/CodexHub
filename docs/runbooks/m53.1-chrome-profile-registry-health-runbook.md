# M53.1 Chrome Profile Registry And Health Runbook

Purpose:

- Use the browser profile kernel to model Chrome profile registration, locking,
  health, checkpoints, and quota readiness without touching real browser state.

## Expected Behavior

The kernel must:

- Hash profile paths before returning profile binding metadata.
- Store display/account/workspace values only as hashes.
- Create profile locks as metadata leases with no lease secret stored.
- Create health records and HumanCheckpoints for human action when profile
  readiness is not healthy.
- Rehearse quota readiness from provided metadata only.
- Keep browser storage reads and external process starts disabled.

## Operator Checks

Before wiring M53 into store or Supervisor:

1. Run `pnpm nx test browser-profile-kernel`.
2. Confirm `pnpm audit:no-live-automation` passes.
3. Confirm no Chrome connector, filesystem profile scan, storage read, or
   external process runner exists in the kernel.
4. Confirm serialized outputs do not contain raw profile paths, account keys,
   workspace keys, holder keys, or quota reset values.
5. Confirm HumanCheckpoints request human action and do not automate login,
   MFA, captcha, or workspace selection.

## Stop Conditions

Stop the round if:

- Any code reads browser tokens, cookies, sessions, MFA state, browser storage,
  or raw profile files.
- A response contains a raw profile path, account key, workspace key, holder key,
  quota reset value, prompt, diff, path, or body.
- A health check attempts to bypass login, MFA, captcha, account limits,
  workspace governance, or quota rules.
- Browser click/input automation appears in the foundation scaffold.

## Extending Later

Use this order:

1. Persist profile registry records through M51 store repositories.
2. Project profile health through Supervisor read routes.
3. Add read-only observation adapters with explicit manifest and dry-run plans.
4. Keep all profile act/input automation disabled until a later approved
   milestone.
5. Require policy, approval, evidence, and audit gates before any profile
   mutation or live recovery operation.

## Closeout Gates

Every follow-up M53 sub-round must run:

- Focused tests for touched packages.
- Focused build for touched packages.
- `pnpm scaffold:health`
- `pnpm audit:boundaries`
- `pnpm audit:sqlite-isolation`
- `pnpm audit:no-live-automation`
- `pnpm audit:skills`
- `git diff --check`

Run `pnpm verify:foundation` at major-stage closeout.

## Rollback

If profile health leaks raw private data or starts touching real browser state,
revert the M53.1 commit and restore the M52.1 adapter baseline.
