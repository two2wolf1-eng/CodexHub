# M53.1 Chrome Profile Registry And Health

Status: completed.

## GSD Spec

- Goal: extend `browser-profile-kernel` with Chrome Profile Registry metadata,
  profile registration dry-run, profile locking, ChatGPT profile health,
  HumanCheckpoint generation, and workspace/quota readiness rehearsal.
- Scope: `packages/browser-profile-kernel`, focused tests, static audit
  metadata allowlist, scaffold health registration, release/review/runbook docs.
- Non-scope: no real Chrome connection, browser profile probing, cookie/token
  extraction, browser storage reads, Supervisor route wiring, account switching,
  or live automation.
- Acceptance criteria: profile registration returns hash-only binding metadata;
  locks create metadata leases; health checks produce M51 health records and
  checkpoints when needed; rehearsal combines profile, workspace, and quota
  metadata; tests prove raw profile path, account, workspace, and reset values
  are not returned.
- Hard boundaries: no token, cookie, session, MFA, credential, browser storage,
  raw profile path, prompt, diff, path, or body is read, returned, or persisted.
- Affected apps/packages: `packages/browser-profile-kernel`,
  `tools/audit-no-live-automation.ts`, docs, and `tools/scaffold-health.ts`.
- Risk level: high, because this prepares real profile governance surfaces while
  keeping the foundation read-only and metadata-only.

## GStack Plan

- Plan: extend the kernel API first, then focused tests and audit docs.
- Build: reuse M51 `ChromeProfileBinding`, `ChatGptSessionHealth`,
  `HumanCheckpoint`, `Lease`, and `QuotaSnapshot` contracts.
- Review: check no browser connection, no storage read, no raw path output, and
  no external process start.
- QA: run focused browser profile test/build and foundation boundary audits.
- Ship: commit independently before any future Supervisor wiring.
- Retro: M53 can model profile readiness and human checkpoints without touching
  real browser state.
